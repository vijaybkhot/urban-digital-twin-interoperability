# Extending the Prototype

This guide is for contributors who want to change what the application shows.
It covers three tasks: adding a new data layer to the urban-resilience demo,
updating an existing layer's data, and adding a new application mode. Each
recipe names every file you will touch, in the order you touch it.

Read [the onboarding guide](onboarding.md) first. It gets the app running and
explains the five modes. This guide assumes you have done that.

## Rules that apply to every change

These are invariants. A change that breaks one of them is wrong even if
`npm run validate` passes.

1. **Only `src/cesium/` and `src/adapters/viewer/` import `cesium`.** Every
   other layer (`src/types`, `src/domain`, `src/ports`, `src/components`,
   `src/app`) stays viewer-independent and reaches the viewer only through the
   `ViewerAdapter` interface in `src/ports/ViewerAdapter.ts`. Check with
   `grep -rln 'from "cesium"' src`.
2. **Scientific processing stays in `scripts/`.** Fetching OSM, FEMA, or USGS
   data, intersecting geometries, and assigning classifications all happen in
   Node scripts that write validated GeoJSON to `public/data/`. The browser
   only reads and displays those committed files. Do not move a spatial
   calculation into a component or a Cesium styler to make a feature easier
   to build.
3. **Every public data artifact needs provenance and a validator.** Follow the
   eight-point checklist in
   [`CONTRIBUTING.md` → Data and provenance requirements](../../CONTRIBUTING.md#data-and-provenance-requirements),
   and the interpretation rules in
   [Scientific and safety language](../../CONTRIBUTING.md#scientific-and-safety-language).
   `Unknown` never becomes `Low`; zero OSM results are a data-availability
   statement, not evidence of absence; nothing is described as official,
   operational, validated, or a forecast.
4. **A new research direction gets an ADR before code.** Write a decision
   record in `docs/decisions/` that states what the new work may and may not
   claim, then build to it. See "The ADR-first pattern" below.

What this guide does **not** cover, deliberately: hazard models, risk scores,
predictive outputs, or anything that would turn a mapped data relationship
into a safety judgment. If you want to add one of those, that is a research
decision for the project leads and needs its own ADR first; it is not an
extension recipe.

## Recipe 1: Add a new data layer

The worked example throughout is the **community/public-safety facility
experiment**: the cleanest complete layer in the repository. It fetches OSM
facilities and FEMA zones, classifies their relationship, renders cyan and
purple markers, has a toggle, a legend, an inspector, and full documentation.
For each step, open the facility file named and copy its shape.

### Step 1. Check the source and its license

Before writing code, confirm the source is public, scriptable, and licensed for
redistribution (OSM is ODbL; FEMA NFHL and USGS 3DEP are U.S. federal public
data). Record the endpoint, license, and query window; you will need them for
the data register in step 4.

Only add a layer if a script can fetch it. A layer that needs a manual
download cannot be regenerated by a successor.

### Step 2. Define the study area

Query windows live in **`scripts/lib/studyAreas.mjs`**. Reuse an existing
bounding box if it fits, or add a new exported constant with a comment
explaining why it differs.

- Facility example: `grandIsleFacilityBbox` (slightly wider than the base
  `grandIsleBaseBbox`, with a comment saying why) and the shared
  `portFourchonBbox`.

### Step 3. Write the fetch / build / validate scripts

Each layer has three Node scripts in `scripts/` and three `package.json`
entries.

| Stage | Facility example | What it does |
| --- | --- | --- |
| fetch | `scripts/fetchUrbanResilienceFacilitySourceData.mjs` (`npm run fetch:urban-resilience-facility-data`) | Calls the external API and writes raw responses to `scripts/.cache/urban-resilience/` (git-ignored). |
| build | `scripts/buildUrbanResilienceFacilityExperiment.mjs` (`npm run build:urban-resilience-facility-data`) | Reads only the cache, does all processing and classification, writes GeoJSON to `public/data/urban-resilience/experiments/community_public_safety_facilities.geojson`. |
| validate | `scripts/validateUrbanResilienceFacilityExperiment.mjs` (`npm run validate:urban-resilience-facility-data`) | Asserts the committed GeoJSON's shape, identities, allowed values, and conservative wording. |

Then add the validate script to the `validate` chain in `package.json`. That
chain is the only CI gate (`.github/workflows/validation.yml` runs
`npm run validate`), so a validator that is not in it never runs.

Things to copy from the facility scripts:

- Each output feature carries its source identifiers (`osm_element_type`,
  `osm_id`), its sources (`osm_source`, `fema_source`), a `processing_method`,
  and an `interpretation` string that says what the record does and does not
  mean.
- Coverage is explicit: a FEMA query that returned nothing produces a
  coverage status and `Unknown`, never a negative finding.
- The validator pins what must not drift silently (the facility validator
  pins all four facilities by name and OSM identity), rejects properties that
  would imply a safety judgment (its `PROHIBITED_FIELDS` list includes
  `operational_status`, `availability`, and `criticality_score`), and
  requires the conservative wording in `interpretation` and
  `processing_method`.
- Shared geometry helpers live in `scripts/lib/` (for example
  `linePolygonIntersection.mjs`, `geoJsonRepresentativePoint.mjs`).

If your build reads another layer's committed output, document the order in
step 4; the elevation sample, for example, depends on the facility output.

### Step 4. Document the data

Add a numbered section to **`docs/data/data-register.md`** (the facility entry
is section 5, "Experimental: Community/Public-Safety Facilities") covering
every point of the CONTRIBUTING provenance checklist, and add your three
commands in the right position in **`docs/data/regeneration.md`**'s
dependency graph and command sequence.

### Step 5. Add the TypeScript types and parser

- **`src/types/urbanResilience.ts`**: an attributes interface for one feature
  (facility example: `UrbanFacilityAttributes`, plus `UrbanFacilityCategory`
  and `UrbanFacilityType`), a `Selected…` type if features are clickable
  (`SelectedUrbanFacility`), and a new data-URL field on
  `UrbanResilienceScenario` (`experimentalFacilityDataUrl`).
- **`src/domain/urbanResilience/urbanResilienceContract.ts`**: the allowed
  value lists (`URBAN_FACILITY_CATEGORIES`, `URBAN_FACILITY_TYPES`).
- **`src/domain/urbanResilience/parseUrbanFacilityAttributes.ts`**: a parser
  that turns raw GeoJSON properties into the typed attributes or returns
  `null`. It must not compute anything new; it only checks and reads.
- **`src/domain/urbanResilience/grandIslePortFourchonScenario.ts`**: set the
  new URL field. This is the **only** place a data URL literal is written.

### Step 6. Register the layer

Add an entry to `urbanResilienceLayers` in
**`src/domain/urbanResilience/urbanResilienceLayerRegistry.ts`** (the design
is explained in [ADR 008](../decisions/008-urban-layer-registry.md)):

- add the new id to the `UrbanLayerId` union, and your scenario field to the
  `UrbanLayerDataUrlKey` union;
- copy the `provenance` fields from the data register; do not invent or
  paraphrase them;
- set `category` (`"experimental"` for anything opt-in), `renderTarget`,
  `defaultVisible`, `toggleable`, and `selectable`;
- add `legend` rows whose `color` comes from
  **`src/theme/urbanResilienceVisualTokens.ts`** (facility example:
  `facilityPublicSafety`, `facilityCommunity`), never a hex literal, and whose
  `symbol` is one of `UrbanLegendSwatchSymbol`. Each symbol needs a matching
  CSS class `urban-map-legend-{symbol}` in
  `src/components/UrbanResilienceDemoPanel/UrbanResilienceDemoPanel.css`; add
  both if you need a new shape.

`defaultUrbanLayerVisibility` and `urbanLegendEntries` pick the new entry up
automatically.

### Step 7. Render it behind the viewer boundary

- **`src/ports/ViewerAdapter.ts`**: add a render method
  (`renderUrbanFacilityExperiment(dataUrl: string | null): Promise<void>`;
  `null` means "remove the layer"). If features are clickable, add a
  `ViewerSelection` variant (`type: "urbanFacility"`) and an id field on
  `ViewerSelectedEntityIds` (`urbanFacilityId`).
- **`src/cesium/styleUrbanFacilityDataSource.ts`**: a styler that reads each
  entity's properties through your parser and applies colors from the token
  file. Keep selected/unselected styling in one function
  (`applyUrbanFacilityVisualState`).
- **`src/adapters/viewer/CesiumViewerAdapter.ts`**: implement the render
  method. Copy the facility pattern exactly: a per-layer load-version counter
  (`urbanFacilityLoadVersion`) checked after every `await`, so a slow load
  cannot overwrite a newer one; a clear method; entity bookkeeping; emitting
  the selection on click; and reapplying highlight state from
  `applySelectionStyles()`. Store any per-entity state in an instance field
  and reapply it there rather than in a setter, which avoids load-order
  races.
- **`src/components/CesiumScene/CesiumScene.tsx`**: add a prop
  (`urbanFacilityExperimentDataUrl`) and an effect that calls the adapter
  method, and passes the selected id into `setSelectedEntityIds`.

### Step 8. Wire state and the panel

- **`src/app/AppShell.tsx`**: pass
  `resolveUrbanLayerDataUrl("<your-layer-id>", urbanScenario)` to the new
  `CesiumScene` prop when the layer is visible, and `null` otherwise. Add
  selection state if clickable (`selectedUrbanFacility`), set it in the
  `onEntitySelected` handler passed to `CesiumScene`, clear the other selections there, clear it in
  `handleUrbanLayerVisibilityChange` when the layer turns off, and clear it in
  every mode-switch callback.
- **`src/components/UrbanResilienceDemoPanel/UrbanResilienceDemoPanel.tsx`**:
  add the toggle to the "Data layers" section with its `role="note"` safety
  text directly beside it. A note may be moved but not reworded without
  review (ADR 006).
- **Inspector** (if clickable): a pure component that takes a non-null
  selection (`UrbanFacilityExperimentPanel.tsx`), shown through
  `UrbanSelectedFeatureSection.tsx`, which already guarantees only one
  inspector renders at a time.

### Step 9. Document the layer and check the panel

- Add a section to **`docs/data/urban-resilience-layers.md`** (facility
  example: section 4) describing load path, styling, toggle, selection, and
  interpretation limits.
- Add checks for the new layer to
  **`docs/urban-resilience-panel-regression-checklist.md`** and run the whole
  checklist in a browser.
- Add a **`docs/devlog.md`** entry.
- Run `npm run validate`, and confirm with `git diff --stat` that nothing
  outside the files above changed.

### Checklist: every file a new layer touches

| Area | Files |
| --- | --- |
| Pipeline | `scripts/lib/studyAreas.mjs`; `scripts/fetch…`, `scripts/build…`, `scripts/validate…`; `package.json`; the generated GeoJSON under `public/data/urban-resilience/` |
| Types and domain | `src/types/urbanResilience.ts`; `src/domain/urbanResilience/urbanResilienceContract.ts`; a new `parse….ts`; `grandIslePortFourchonScenario.ts`; `urbanResilienceLayerRegistry.ts`; `src/theme/urbanResilienceVisualTokens.ts` |
| Viewer | `src/ports/ViewerAdapter.ts`; a new `src/cesium/style….ts`; `src/adapters/viewer/CesiumViewerAdapter.ts`; `src/components/CesiumScene/CesiumScene.tsx` |
| UI | `src/app/AppShell.tsx`; `UrbanResilienceDemoPanel.tsx` and `.css`; an inspector component and `UrbanSelectedFeatureSection.tsx` if clickable |
| Docs | `docs/data/data-register.md`; `docs/data/regeneration.md`; `docs/data/urban-resilience-layers.md`; `docs/urban-resilience-panel-regression-checklist.md`; `docs/devlog.md` |

## Recipe 2: Update an existing layer's data

Regenerating data is a research activity, not a mechanical update: upstream
OSM and FEMA data change, and a re-fetch can silently change what a dataset
describes.

1. **Read [`docs/data/regeneration.md`](../data/regeneration.md) end to end
   first.** It gives the required order. The four pipelines are not
   independent: the LA-1 experiment reuses the base fetch cache, and the
   elevation sample reads the committed outputs of the base and facility
   builds, so it must run last.
2. **Expect the pinned-manifest check to fail if OSM changed.** Property ids
   (`GI-0001`, …) are assigned in Overpass response order, so a single OSM edit
   can shift them. `scripts/lib/urbanElevationSample.mjs` pins 12 buildings
   and 4 facilities, and the facility validator pins the 4 facilities by name
   and OSM identity. Follow the migration procedure in
   [regeneration.md → "The pinned-manifest hazard, and its migration procedure"](../data/regeneration.md#the-pinned-manifest-hazard-and-its-migration-procedure):
   diff the new output against the committed one, decide whether re-pinning is
   justified, update `SAMPLED_GRAND_ISLE_BUILDINGS` /
   `EXPECTED_GRAND_ISLE_FACILITIES` / the validator's `EXPECTED_FACILITIES`,
   and **never weaken a pinned assertion to make a regeneration pass**.
3. **Write a provenance note.** Any change to what a dataset covers (different
   buildings sampled, different counts, a new retrieval date) gets a
   `docs/devlog.md` entry and updates to the dataset's section in
   `docs/data/data-register.md`, and to `docs/data/urban-resilience-layers.md`
   if counts or behavior changed.
4. **Run `npm run validate`** and review the GeoJSON diff before committing.

CI never runs a `fetch:*` script, so upstream drift is only noticed when a
person regenerates. That is deliberate; see "CI does not run any `fetch:*`
script" in `regeneration.md`.

## Recipe 3: Add a new application mode

A mode is a separate scenario with its own contract, panel, and rendering,
sharing only the viewer. The disaster-resilience and modular-housing modes
are the closest examples.

1. **Write the ADR first** (see the next section). Decide whether the mode is
   `mock`, `fictional`, or `research-real-data`; that classification is a
   safety property, not a label.
2. **Register the mode** in **`src/types/applicationMode.ts`**: add the id to
   the `ApplicationMode` union and an entry to `APPLICATION_MODES` with its
   single canonical `label`, its `kind`, and `isPrimary: false`. The
   `ModeSwitcher` (`src/components/ModeSwitcher/`) lists it under "Other demo
   modes" automatically.
3. **Add a typed scenario contract**: `src/types/<mode>.ts` and
   `src/domain/<mode>/` (example: `src/types/disasterResilience.ts` and
   `src/domain/disasterResilience/`, including
   `createDisasterResilienceViewerConfig.ts`). Do not extend
   `public/project_config.json` with fields for an unrelated domain.
4. **Render behind the port**: a `render…Scenario` method on `ViewerAdapter`,
   its implementation in `CesiumViewerAdapter.ts`, entity builders in
   `src/cesium/` (example: `createDisasterResponseEntities.ts`,
   `styleDisasterPropertyDataSource.ts`), and the matching prop on
   `CesiumScene.tsx`.
5. **Add an open callback in `src/app/AppShell.tsx`** modelled on
   `openDisasterDemo`. Every open callback must reset all other modes' state:
   bump `navigationVersionRef`, clear every selection, reset
   `setUrbanLayerVisibility(defaultUrbanLayerVisibility)`, then `setMode(...)`.
   If your mode has its own state, also reset it in every existing open
   callback. Then add a `case` to `selectMode` and the mode's config to the
   `activeConfig` chain.
6. **Add a panel** in `src/components/<ModeName>Panel/` that shows the mode's
   disclaimer prominently.
7. **Document it**: the mode list in `README.md` and `docs/architecture.md`,
   the mode table in `docs/handoff/onboarding.md`, and any data in
   `docs/data/data-register.md`.

## Keep Cesium-facing objects stable

`CesiumScene` effects run when the identity of their inputs changes, not
their contents. If a config object, scenario, or visibility record is rebuilt
on every render, the adapter clears and redraws the layer, and may refetch
its GeoJSON, even though nothing meaningful changed.

- Hold scenario data in `useState` and derive viewer config with `useMemo`
  (as `AppShell` does for `urbanScenario` and `urbanViewerConfig`).
- Build records such as the layer-visibility state from a shared default
  (`defaultUrbanLayerVisibility`), never as an object literal inline in JSX.
- When live runtime status changes (an event, a selection), update that state
  alone; do not rebuild the whole viewer config from it.
- When several entities share a derived status, decide whether it is
  per-entity or aggregated, and compute aggregates from live entity state
  instead of mutating a shared field.

This bug class has been found twice independently: in the modular demo
(closed issue #34) and while designing the urban layer registry (HO-18/HO-19).

## The ADR-first pattern

The two scenario ADRs show what a research guardrail looks like before any
code exists:

- [ADR 005: Modular Housing Demo Guardrails](../decisions/005-modular-housing-demo-guardrails.md)
  fixed that the modular demo is a mock proposal scenario with its own
  contract, isolated from the existing demo's data.
- [ADR 006: Urban Resilience Real-Data Guardrails](../decisions/006-urban-resilience-real-data-guardrails.md)
  fixed what real public data may be used to claim: zone-based
  classification as a documented proxy, `Unknown` for coverage gaps, and
  safety wording that is bound to specific claims.

A new ADR should state the context, the decision, what the work may claim,
what it must never claim, and how a reviewer can check that. Number it next in
sequence in `docs/decisions/`, get it reviewed, then implement.
